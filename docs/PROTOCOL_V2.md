# ADC-100 Secure Protocol v2

This document is the contract between the **firmware** (`production` branch of
ADC_100_Controller) and the **dashboard** (`src/devicesig.js`). Both sides must
produce byte-identical messages. There are conformance vectors in
`tests/vectors_v2.json` (generated by the dashboard, verified by a C host test).

## Why v2

| v1 problem | v2 fix |
|---|---|
| One shared secret in every firmware image | One key **per device**, written at provisioning, never in the image |
| Signature covered only `cmd:ts` | Signature covers device id, nonce **and every security-relevant field** (OTA url, credential data, Wi-Fi, ...) |
| A signed command was valid on any device / on `adc100/doors/all` | Signature contains the device id; the broadcast topic is not used |
| Temporary QR valid on every door | Temporary QR contains and is signed for one device id |
| BLE default key `ADC100-DEFAULT-KEY` | BLE key derived per device; no default key in production |
| Broker credentials hard-coded in source | Read from NVS (provisioned) |

## Keys

```
MASTER      32+ random bytes, only on the dashboard server (env DEVICE_MASTER_KEY)
            and in the provisioning tool. NEVER in firmware.
device_key  = HMAC-SHA256(MASTER, "adc100-device-key-v1\n" + device_id)      (32 bytes)
ble_key     = HMAC-SHA256(device_key, "adc100-ble-key-v1")                   (32 bytes)
```

`device_id` is the MQTT id of the device (`devices.mqtt_id`), the same string the
firmware uses in its topics (`adc100/<device_id>/cmd`).

The device stores only `device_key` (32 raw bytes). It derives `ble_key` itself.
Compromising one device reveals that device's key only.

## Signed command (MQTT, topic `adc100/<device_id>/cmd`)

```json
{"cmd":"open","ts":1760000000,"v":2,"n":"a1b2c3d4e5f60718","hmac":"<64 hex>",
 "relay_mode":"timed","relay_duration":5}
```

* `ts`   unix seconds. Device accepts `|now - ts| <= 30` (needs NTP).
* `v`    must be `2`.
* `n`    nonce, 16 lowercase hex chars (8 random bytes). Unique per command.
         The device remembers recent nonces and rejects a repeat (replay).
* `hmac` lowercase hex of `HMAC-SHA256(device_key, MSG)`.

```
MSG = "v2\n" + device_id + "\n" + cmd + "\n" + ts + "\n" + n + "\n"
      + for each signed field of that command, in the table order below:
            len(value_utf8_bytes) + ":" + value + "\n"
```

A field that is absent is signed as the empty string (`0:`). Numeric fields are
signed as their decimal text (`5`). Strings are signed exactly as the device
parser returns them. Length-prefixing makes the encoding unambiguous.

### Signed fields per command

| cmd | fields (in order) |
|---|---|
| `open` | `relay_mode`, `relay_duration` |
| `set_schedule` | `enabled`, `start`, `end` |
| `add_credential` | `cred_type`, `cred_data`, `label`, `duress` |
| `delete_credential` | `label` |
| `clear_credentials` | (none) |
| `set_touch` | `enabled` |
| `set_wifi` | `ssid`, `pass` |
| `apply_wifi`, `reset_wifi`, `restart`, `get_status`, `get_logs`, `clear_logs` | (none) |
| `ota_update` | `url` |
| `set_ble_name` | `name` |

An unknown `cmd` is rejected.

## Temporary QR v2

QR content (compact JSON, this exact key order, about 85 bytes):

```json
{"v":2,"iat":1760000000,"exp":1760003600,"hmac":"<32 hex>"}
```
```
MSG  = "v2tqr\n" + device_id + "\n" + iat + "\n" + exp
hmac = first 32 hex chars (128 bit) of HMAC-SHA256(device_key, MSG)
```

The door id is **not** in the QR. Each door computes MSG with its own id, so a QR issued
for another door fails the check. The device rejects the QR unless the time window is
valid and the HMAC matches. The firmware recognises it by the prefix `{"v":2,`.

Size limit: the reader sends the controller at most 112 bytes per frame
(`RS485_DATA_MAX`), so the QR must stay below that. A long door id never changes the
QR length because the id is not part of it.

## Provisioning (NVS namespace `adc_sec`)

| key | type | content |
|---|---|---|
| `dev_key` | blob(32) | device_key |
| `mqtt_uri` | string | e.g. `mqtts://host:8883` |
| `mqtt_user` | string | broker user |
| `mqtt_pass` | string | broker password |
| `legacy_off` | u8 | 1 = never accept v1 signatures again (set automatically after migration) |

Two ways to provision:

1. **Factory** — flash an NVS image generated from the dashboard export
   (`nvs_partition_gen.py`). Wi-Fi/credentials are not touched if you use
   `nvs_partial` merge tooling; on a brand-new board the whole NVS is written.
2. **In the field (one time)** — a transition firmware built with
   `CONFIG_ADC_LEGACY_SECRET` accepts exactly one v1-signed command:
   `provision_v2` `{ "dev_key":"<64 hex>" }` while `dev_key` is not yet stored.
   It stores the key, sets `legacy_off=1`, and answers with the event
   `{"event":"provision","result":"OK"}`. From then on only v2 is accepted.

## Dashboard state

`devices.key_version`: `1` legacy (shared secret, v1 messages), `2` provisioned
(v2 messages). The dashboard chooses the format per device.

## Compatibility rules

* A build **without** `CONFIG_ADC_LEGACY_SECRET` (the repository default) has no
  shared secret at all and accepts only v2.
* A transition build sets the legacy secret locally (never committed) so that
  deployed devices can be migrated, then is replaced by a normal build.
